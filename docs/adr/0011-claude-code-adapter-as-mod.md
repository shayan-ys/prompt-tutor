# Claude Code Prompts are queued by a capture-only mod and reviewed by an omp drainer

Status: Accepted (2026-10-09). Research: [issue #21](https://github.com/shayan-ys/prompt-tutor/issues/21) ([findings](https://github.com/shayan-ys/prompt-tutor/blob/research/claude-code-mods/docs/research/claude-code-mods.md)).

prompt-tutor also reviews Prompts typed into Claude Code. A [Claude Mod](https://code.claude.com/docs/en/plugins/mods/overview) (Claude Code 2.1.287 or later) only captures them. On `prompt.submit` with `origin.kind === "composer"`, it passes the Prompt text on stdin to `prompt-tutor capture --harness claude-code`, which writes a `pending` Prompt record (`harness: "claude-code"`) into the Scope store. The mod returns `next(e)` unchanged and never calls a model, so nothing reaches Claude's context. The user starts the review side explicitly: `prompt-tutor drain` runs one headless omp process per configured `review_profile` (`omp [--profile P] --mode rpc --no-ui --no-session` with `PROMPT_TUTOR_DRAIN=1`). In each process the prompt-tutor extension grades that profile's queued records one at a time with the profile's `@task`, using the existing `review()` path. The Watcher and the Review log then show the results with no extra step.

Other designs were rejected:

- **Review inside the mod with `$.model.complete`** (this ADR's first draft). It needs a second grading path: JSON-text output instead of the forced tool, Claude model names instead of omp roles, a split `review()`, and recovery for Reviews killed by `/exit`. It also cannot route the Digest safely. Digest selection (`dueDigests`) matches a Scope by `digest_profile` regardless of cwd, so a fixed `claude-code` profile would send every such Scope's Findings through whichever Claude account was signed in. ADR 0007 rejects exactly this.
- **Every omp session drains the queue.** Any open session could grade any queued record, so the provider would depend on which sessions happened to be open. Two sessions would also race for the same record.
- **A standalone reviewer with its own API key.** It adds a secret for each Scope and a daemon, and gives up omp's per-profile role routing.

## Consequences

- **Who reviews.** A Scope's new `review_profile` names the only omp profile allowed to drain its Claude Code records. It has no default. If a Scope has no `review_profile`, its Claude Code records stay `pending` and are never graded under some other profile's provider. A Scope with Claude Code records but no `review_profile` shows as queued in the Watcher.
- **One drainer per Scope.** A drainer must hold `<store>/drain.lock` to drain a Scope. The lock holds the drainer's PID and profile, and is created atomically (temporary file, then `link`). It is stale when that PID is no longer alive. `prompt-tutor drain` removes a child's lock after that child exits, because omp can exit on a signal without running exit handlers. `prompt-tutor drain` refuses to start a Scope whose lock is held by a live PID ("already draining"). An omp process that loses the race skips that Scope, and a drainer re-checks that it still holds the lock before each record. Two drainers therefore never grade the same record.
- **No regrading of lost omp Reviews.** Drainers only take `harness: "claude-code"` records, so omp's own Review path is unchanged. A queued record stays `pending` until a drainer grades it, and closing Claude Code loses nothing. Nothing regrades `pending` omp records. The earlier draft's "regrade after 10 minutes" rule is dropped.
- **Watcher.** A pending Claude Code Prompt shows `queued` while no live drainer holds its Scope's lock, and the normal spinner while one does. The Review log is unchanged.
- **Scope matching.** A Claude Code record stores `profile: "claude-code"` and the session cwd. So `when.cwd` works as it does for omp, and `when: - profile: claude-code` can target Claude Code Prompts. A Scope matched only by `profile:` conditions for omp profiles does not receive Claude Code Prompts.
- **Digest and retention stay in omp.** Claude Code never runs a Digest or a prune. The drainer's omp processes are ordinary sessions of their profiles, so `session_start` also runs their Digest and retention work under ADR 0007 and ADR 0009.
- **Provider exposure.** A Claude Code Prompt in a Scope goes to the `@task` model of that Scope's `review_profile`, not to the Claude account. The README privacy section says this.
- **Capture rules.** Slash-command Prompts arrive as typed and go through the existing preprocessing. `bridge` (Remote Control), `sdk` (`claude -p`, the Agent SDK), notifications, `/loop`, schedules, peers, and other plugins are not captured. The mod captures in a `$.clock.after(0)` job. In Claude Code it shows only a `$.ui.status` notice when a capture fails, which never reaches the model. It never writes to `$.ui.log`, because those lines are saved in Claude's transcript files.
- **Requirements.** `prompt-tutor` and Bun must be on the PATH that Claude Code runs with (`/prompt-tutor install-watcher`). The plugin lives in `claude-code/` with a `.claude-plugin/marketplace.json` at the repository root.
- **Risk.** Mods are new, and every release since 2.1.287 has fixed mod bugs, so the mod stays a few lines long. An organization's managed `allowManagedModsOnly`, `allowManagedHooksOnly`, or `disableAllHooks` turns the mod off without notice. Captures then simply stop. On 2026-10-09, `$.settings.read` showed none of these on Shayan's Claude Team sign-in.
- **Scope of the product.** The spec's scope line now names a Claude Code capture adapter and an explicitly started drainer. Daemons and scheduled jobs remain out of scope: the drainer runs only while the user keeps it running.
