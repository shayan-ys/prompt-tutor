# omp distribution: GitHub extension and Watcher install

Research checked against the omp 18.6.1 installed documentation and the matching upstream `v18.6.1` source. The repo checkout and user `~/.omp` directories were not modified or installed into during this research.

## Answers

1. **Partly.** `omp plugin install` accepts GitHub shorthands such as `github:owner/repo` and Git URLs. For omp to load the repo as a plugin, it must have a `package.json` with an `omp` (or legacy `pi`) manifest; extension entries are declared in `package.json#omp.extensions`. The plugin manager installs the package in its plugin `node_modules` and registers those extension entries. A Marketplace can also install GitHub-sourced plugins, but the Marketplace repo must provide an `.omp-plugin/marketplace.json` (or compatible `.claude-plugin/marketplace.json`) catalog. **Neither route puts the Watcher’s `package.json#bin` executable on the user’s `PATH`**: the plugin manager installs into its plugin tree and has no PATH/bin installation step. So omp can manage the extension, but not the complete extension-plus-PATH-executable install as one operation. [Plugin manager docs](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/plugin-manager-installer-plumbing.md#install-spec-grammar) · [Marketplace docs](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/marketplace.md#marketplace-sources) · [Plugin manager source](https://github.com/can1357/oh-my-pi/blob/v18.6.1/packages/coding-agent/src/extensibility/plugins/manager.ts) · [Extension loading docs](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/extension-loading.md#installed-plugin-extension-entries)

2. **Partly.** A repo clone plus a symlink to its extension module/directory is compatible with native extension discovery: symlinks are eligible extension files/directories. The default user target is `~/.omp/agent/extensions/<name>`; for a named profile it is `~/.omp/profiles/<profile>/agent/extensions/<name>`. A project-only alternative is `<project>/.omp/extensions/<name>`. The Watcher symlink must instead target a directory already on the user’s shell `PATH`; omp defines no bin-scripts directory. On this machine `~/.local/bin` is already on `PATH`, so that is a suitable target here; elsewhere use a PATH directory configured on that machine. This manual extension-directory symlink is supported by discovery, but is not a dedicated omp install/uninstall command. [`extension-loading.md`](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/extension-loading.md#inputs-to-extension-loading) · [`config-usage.md`](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/config-usage.md#profiles)

3. **No, not by installing into one profile’s user directory.** Each named profile uses its own OMP-native user config and extension directory; a named profile does not inherit the default profile’s agent config. The least surprising cross-profile setup is one shared source checkout, a symlink for the extension in each profile’s own `agent/extensions/`, and one Watcher symlink in a PATH directory. For example:

   ```text
   <checkout>/<extension-entry> -> ~/.omp/agent/extensions/<name>                         # default
   <checkout>/<extension-entry> -> ~/.omp/profiles/personal/agent/extensions/<name>
   <checkout>/<extension-entry> -> ~/.omp/profiles/work/agent/extensions/<name>
   <checkout>/<watcher-script>  -> ~/.local/bin/<watcher-command>                        # if on PATH
   ```

   Alternatively, use the plugin/Marketplace manager separately with each profile selected; its named-profile roots are profile-specific too. A project-level `<project>/.omp/extensions/` install is shared across profiles only when running in that project. [`config-usage.md`](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/config-usage.md#profiles) · [`extension-loading.md`](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/extension-loading.md#inputs-to-extension-loading) · [`plugin-manager-installer-plumbing.md`](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/plugin-manager-installer-plumbing.md#on-disk-model)

4. **Upgrade/uninstall by option:**
   - **Direct Git/npm plugin:** `omp plugin upgrade <package-name>` re-resolves the recorded Git ref (or moves an npm package to its latest version) and preserves enabled state/feature selection. `omp plugin uninstall <package-name>` removes the package and its plugin runtime state. Do this in each profile where it was separately installed. [`plugin-manager-installer-plumbing.md`](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/plugin-manager-installer-plumbing.md#update-semantics) · [Manager source](https://github.com/can1357/oh-my-pi/blob/v18.6.1/packages/coding-agent/src/extensibility/plugins/manager.ts)
   - **Marketplace:** `omp plugin marketplace update [name]` refreshes catalog metadata only; then `omp plugin upgrade <name@marketplace>` upgrades installed plugins. `omp plugin uninstall <name@marketplace>` removes the install (specify `--scope user|project` when needed to disambiguate). Removing the Marketplace does **not** uninstall its already-installed plugins. [`marketplace.md`](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/marketplace.md#updates-removal-and-scope)
   - **Shared clone and symlinks:** update the checkout with Git; the symlinks then point at the updated files. Restart omp to load changed extension code: extension modules are not unloaded or re-evaluated by live settings reconciliation, and newly enabled modules require a restart. Uninstall by removing the extension symlink from each profile and the Watcher symlink from `PATH`; remove the checkout only if nothing else uses it. [`extension-loading.md`](https://github.com/can1357/oh-my-pi/blob/v18.6.1/docs/extension-loading.md#live-source-changes)

## Implications for the design

- **Settled decisions hold:** ADR 0001’s per-Prompt JSON storage and ADR 0002’s just-in-time Digest are unaffected. ADR 0003’s `@advisor` grading decision is also unaffected; this distribution research does not verify the extension API/model-call contract that ADR 0003 explicitly left for the extension-API research ticket. [ADR 0001](../adr/0001-per-prompt-json-files.md) · [ADR 0002](../adr/0002-just-in-time-digest.md) · [ADR 0003](../adr/0003-grader-via-advisor-role.md)
- **No ADR needs to change based on this research.** The install story must distinguish the extension from the Watcher executable: omp can manage a Git plugin declaring `omp.extensions`, but PATH exposure remains a separate user-level link/install step. A single profile-scoped plugin install is not automatically shared with other profiles.
- **Follow-up grilling question:** Which is prompt-tutor’s canonical distribution contract: (a) direct Git plugin install, (b) a published omp Marketplace catalog, or (c) shared clone + symlinks—and exactly how should the Watcher be placed on `PATH` and maintained across named profiles? The choice should specify the user-facing upgrade/uninstall steps and whether each profile gets its own managed plugin install or a shared checkout with per-profile extension links.
